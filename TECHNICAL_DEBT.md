# Q-Trust Technical Debt Register

Living document. Priority: P1 (schedule) / P2 (plan) / P3 (opportunistic).

| # | Debt | Impact | Why It Exists | Recommended Resolution | Priority |
|---|---|---|---|---|---|
| TD-01 | `frontend/src/components/scanner-dashboard.tsx` is ~1,200 lines mixing data fetching, layout, and export logic | Slower reviews, higher regression risk on every scanner change | Grew organically with scanner features | Split into `ScannerResults`, `ScannerExportBar`, `ScannerFilters` with tests moved per component | P2 |
| TD-02 | Shipped model checkpoints lack an in-artifact epoch/version manifest (only config.json) | Cannot prove which script version produced a checkpoint | Checkpoint predates the artifact-metadata convention | Add `training_manifest.json` next time any checkpoint is regenerated; record epochs, git SHA, dataset hash | P2 |
| TD-03 | Two documentation systems (mkdocs `docs/` + `docs-v2/` Vite site) | Double maintenance, drift risk | docs-v2 added as a modern site later; mkdocs remains the API/reference home | Long-term: fold mkdocs reference content into docs-v2 or generate one from the other | P3 |
| TD-04 | Contract test suite covers pause/roles/adversarial paths, but no property-based (Echidna/Foundry invariant) fuzzer run is automated | Deep invariant violations could hide beyond hand-written tests | Fuzzing infra not yet wired into CI | Add a nightly Foundry invariant job with the timelock-delay and registry-count invariants already written | P2 |
| TD-05 | `scripts/verify_all.sh` runs ~20 min serially; slows release confidence loops | Release engineering friction | Aggregates every suite into one gate | Shard into a matrix (Python / contracts / Node) like CI already does | P3 |
| TD-06 | Frontend had no automated Lighthouse/CWV budget in CI | Perf regressions would ship silently | Playwright covered function+a11y, not perf | **CLOSED 2026-09-08** — `frontend/e2e/cwv-budget.spec.ts` gates LCP ≤ 2.5 s + CLS ≤ 0.1 (PerformanceObserver) in the existing e2e job; the full Lighthouse toolchain remains an optional manual run | P3 |
| TD-07 | The proxy's authorization policy was inline and private, so the UI had no way to know which endpoints it could reach. The scanner, GPU, planner and attestation surfaces all called privileged routes the proxy denies by default, making those controls permanently 403 in any deployment using the same-origin proxy. Component tests stubbed `fetch` and could not see it | A large share of the product's interactive surface was non-functional in the documented deployment path while every suite reported green | Policy and UI evolved separately; no artifact compared the two endpoint lists | **CLOSED 2026-09-12** — policy extracted to `frontend/src/lib/api-route-policy.ts` (one source of truth for proxy + UI); operator-key path added so privileged routes work for a caller holding a key while anonymous callers stay denied; `lib/__tests__/api-route-policy.test.ts` scans UI source and fails on any unclassified endpoint | P1 |
| TD-09 | The automated a11y gate (`frontend/e2e/a11y.spec.ts`) audited only the *empty* states of each route: every scanner panel fills in only after a privileged round trip, so the result tables, status pills, score bars, roadmap timeline and evidence ledger had never been scanned | A contrast or labelling regression in a post-scan state would ship undetected — exactly how the seven AA contrast failures fixed on 2026-09-12 stayed hidden | The gate drives a dev server with no backend, so it can only see what renders without one | **CLOSED 2026-09-12** — `frontend/e2e/a11y-app.spec.ts` mocks the backend, seeds an operator key, drives a scan and audits all five tabs at both configured viewports; each test asserts its panel actually rendered fixture data first, so it cannot pass vacuously. It immediately found a 52-node AA failure (`--color-muted-foreground` #64748b on `--color-muted` = 4.34:1) that had been live in the empty-state-only world for as long as the token existed. Residual scope — the wallet-gated `/dashboard` and `/vendors` — moved to TD-12 | P2 |
| TD-09a | *Partial closure of TD-09 (2026-09-12).* `/v/[id]` now runs on every a11y invocation. It previously sat behind `test.skip(process.env.QTRUST_E2E_PUBLIC_PAGE !== "1")` **and** a second skip on any non-200 response; the env var is set nowhere in the repo, so the route had never been audited — and the condition that would have exposed its 500 was the same condition that silenced the test. Turning it on immediately surfaced five unlabelled scrollable code regions | — | — | Keep the remaining scope of TD-09 open: post-scan (`/scanner` results) and authenticated (`/dashboard`, `/vendors`) states are still unscanned | — |
| TD-10 | The application layer (`scanner-dashboard.tsx` at ~1,238 lines, `dashboard/page.tsx`, `vendors/page.tsx`, and the `ui/` primitives) still hand-rolled slate card markup instead of consuming the design-token layer | The public and application surfaces shared a shell, typography and canvas but not a component vocabulary; panels written before the tokens existed sat alongside panels that used them | The app layer predated the token layer | **CLOSED 2026-09-12** — semantic state palette + named type scale added to `globals.css`; `ui/status-pill.tsx`, `ui/panel.tsx`, `ui/state.tsx` introduced; every app-layer surface migrated (`scanner-dashboard.tsx`: 101 raw palette utilities → 4, all four inside a comment). Same-status-different-hue is gone, and the compliance chips' ~2.8:1 contrast failure with it. Residual: `scanner-dashboard.tsx` is still ~1,250 lines (TD-01) | P2 |
| TD-11 | No real theme system. `:root` declares `color-scheme: light`, `body` is a dark chrome frame and each route opts into a light or dark surface by hand | A genuine light/dark mode cannot be added without auditing every route, and native controls (scrollbars, form controls) inside the dark header/footer render in the light scheme | The product has always been a dark marketing surface plus a light application layer; there was no requirement for user-selectable theming | Defer until there is a requirement. If added, define both palettes as tokens first and verify with the existing axe gate at each route rather than inverting colours | P3 |
| TD-12 | The wallet-gated surfaces (`/dashboard`, `/vendors`) are still outside the automated a11y gate: reaching them requires a connected wallet, which the e2e suite deliberately does not fake end-to-end | A contrast or labelling regression behind the wallet gate ships undetected | Splitting TD-09 from the wallet problem: mocking the *backend* was enough for `/scanner`, but these pages gate on `useAccount` state, not on a request | Inject a mocked wallet/account hook (or a Playwright-injected `window.ethereum`) so the connected state renders, then audit it with the same `axe-audit.ts` helper. Until then, treat the wallet-gated surfaces as visually unreviewed | P2 |
| TD-08 | The operator API key is held in browser `sessionStorage`, so XSS on the frontend origin is equivalent to key disclosure (accepted) | A compromised script could use the operator's privileged access until the key is revoked | Privileged routes cannot be authorized by the server-side admin key (that was the S-1 vulnerability), so authorization must come from the caller | Accepted for now — key is operator-supplied, revocable, session-scoped, never logged, and production CSP forbids inline/remote scripts. Issue a distinct key per operator (the backend supports `QTRUST_API_KEYS` lists) so one can be revoked independently; revisit with short-lived key exchange if the operator surface grows. Tracked as TM-FE-03 | P3 |
