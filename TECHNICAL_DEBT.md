| TD-08 | The operator API key is held in browser `sessionStorage`, so XSS on the frontend origin is equivalent to key disclosure (accepted) | A compromised script could use the operator's privileged access until the key is revoked | Privileged routes cannot be authorized by the server-side admin key (that was the S-1 vulnerability), so authorization must come from the caller | Accepted for now — key is operator-supplied, revocable, session-scoped, never logged, and production CSP forbids inline/remote scripts. Issue a distinct key per operator (the backend supports `QTRUST_API_KEYS` lists) so one can be revoked independently; revisit with short-lived key exchange if the operator surface grows. Tracked as TM-FE-03 | P3 |
| TD-13 | Issuer-key rotation/revocation for certification bundles is not operationalized. Verification accepts a pinned `trust_anchor_did`, but there is no runbook or status mechanism for retiring a key | A compromised issuer key could keep signing bundles accepted by verifiers that pin the old DID; no way to announce rotation | Bundles were added this session; key lifecycle was out of scope | **CLOSED 2026-10-25** — `docs/runbook/issuer-key-rotation.md` (properties of a rotation, planned procedure with a canary issue/verify across TS + Python, overlap window sized from the policy's `max_validity_days`, SEV1 compromise procedure) plus the discovery surface a rotation needs: `GET /v1/certify/issuer` and `npm run certify:issuer` publish the signing DID, `verificationMethod`, multibase key and SHA-256 fingerprint — public material only, 503 fail-closed when no seed is configured, classified `public-read` in the proxy so a caller can pin before a bundle arrives. Tests pin identity == bundle issuer byte-for-byte. Residual: no machine-readable key *history* verifiers can cache (TD-16) | CLOSED |

| TD-16 | No machine-readable issuer-key *history*. `GET /v1/certify/issuer` publishes only the DID configured right now, and `/v1/certify/verify` takes a single `trust_anchor_did` | Through a rotation's overlap window a pinned verifier must hard-code both DIDs, and after a compromise there is no artifact recording which key was authoritative for which period — the runbook's "publish the list to affected customers" (`docs/runbook/issuer-key-rotation.md:139`) is a manual email, not something a verifier can check | The rotation runbook was written before there was a machine-readable place to put the answer | Add `key_history: [{ issuer, key_fingerprint, valid_from, valid_until, status: active / retired / compromised }]` to the issuer-identity response, sourced from a versioned `QTRUST_VC_ISSUER_KEY_HISTORY` file, and accept `trust_anchor_dids` (list) in verify so a pinned verifier can hold a whole window. Mirror the shape in the SDK. Effort 1 d incl. tests | P2 |\r
| TD-17 | The certification fixture was not reproducible **and** the CI gate that claimed to prove reproducibility could not fail | Two defects, both measured: `bundle_id` was `urn:uuid:${randomUUID()}` while `backend/scripts/make-certification-fixture.ts` and `backend/tests/certification-fixture.test.ts` both documented the fixture as deterministic — two consecutive `npm run certify:fixture` runs differed in `bundle_id`, `digest` and `proof`; and the old `ci.yml` step ran `git diff --exit-code` on `../sdk/tests/fixtures/certification_bundle.json`, a path no commit contains (`git ls-files sdk/tests/fixtures` was empty), so the diff exited 0 whatever the generator wrote. The TS→Python byte-compatibility contract was unprotected in both directions | The bundles, their fixture and that gate were all added in the same uncommitted session, so the step never had a tracked file to diff against | **CLOSED 2026-10-25** — `bundle_id` is now a content-derived name-based UUID (SHA-256 over the canonical bundle with the id omitted, RFC 4122 bit layout; `bundleId()` in `backend/src/services/certification.ts`), the same principle as the keccak256 registry ids in ADR 0006, so re-issuing an unchanged assertion reproduces the bundle byte for byte. Measured: two `npm run certify:fixture` runs plus a third after refactoring the audit gate return identical bytes (`cmp` clean), and `sdk/tests/test_bundle.py` verifies the regenerated file. The CI step now refuses to run vacuously (fails with `::error::` if the fixture is untracked, mirroring the ABI-drift gate at `ci.yml:396`) and then `cmp`s a regeneration against `git show HEAD:` bytes. Tests pin the property both ways: identical inputs → one id and identical JSON; a later clock, a different org or different evidence → a different id. Residual: `sdk/tests/fixtures/certification_bundle.json` is still untracked in the working tree, so the gate fails until it is committed — deliberately, since a fixture nobody versioned is a fixture nobody diffs | CLOSED |
